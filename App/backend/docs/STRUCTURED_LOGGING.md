# Structured Logging

The API Error Logger uses structured logging in JSON format to provide consistent, machine-readable logs that can be easily parsed and analyzed.

## Features

- **JSON Format**: All logs are output in JSON format for easy parsing
- **Request Tracing**: Each request is assigned a unique request ID for end-to-end tracing
- **Event Types**: Logs are categorized by event type for easy filtering
- **Log Levels**: Standard log levels (info, warn, error, debug) for severity classification
- **Metadata**: Rich metadata included with each log entry

## Log Structure

Each log entry follows this structure:

```json
{
  "timestamp": "2024-01-15T10:30:45.123Z",
  "level": "info",
  "message": "Human-readable message",
  "event": "event_type",
  "requestId": "abc123...",
  ...additional metadata
}
```

## Event Types

### Error Submission Events

**Event**: `error_submission`

Logged when an error report is submitted, validated, or completed.

```json
{
  "timestamp": "2024-01-15T10:30:45.123Z",
  "level": "info",
  "message": "Error submission",
  "requestId": "abc123...",
  "event": "error_submission",
  "status": "received|validated|completed|validation_failed|email_failed",
  "endpoint": "/api/users",
  "method": "POST",
  "hasUserContact": true
}
```

### Validation Events

**Event**: `validation_result`

Logged when request validation completes.

```json
{
  "timestamp": "2024-01-15T10:30:45.123Z",
  "level": "info|warn",
  "message": "Validation result",
  "requestId": "abc123...",
  "event": "validation_result",
  "isValid": true,
  "endpoint": "/api/users",
  "method": "POST",
  "errorCount": 0,
  "errors": ["error1", "error2"]  // Only present if validation failed
}
```

### Email Delivery Events

**Event**: `email_delivery`

Logged for each email delivery attempt.

```json
{
  "timestamp": "2024-01-15T10:30:45.123Z",
  "level": "info|error",
  "message": "Email delivery attempt",
  "requestId": "abc123...",
  "event": "email_delivery",
  "status": "sending|sent|failed|retrying",
  "attempt": 1,
  "endpoint": "/api/users",
  "recipientCount": 2,
  "error": "SMTP connection failed"  // Only present if failed
}
```

### Environment Status Events

**Event**: `environment_status_change`

Logged when an environment's status changes.

```json
{
  "timestamp": "2024-01-15T10:30:45.123Z",
  "level": "info",
  "message": "Environment status change",
  "event": "environment_status_change",
  "environment": "Production",
  "previousStatus": "active",
  "newStatus": "inactive",
  "changed": true
}
```

**Event**: `environment_health_check`

Logged for each environment health check (debug level).

```json
{
  "timestamp": "2024-01-15T10:30:45.123Z",
  "level": "debug",
  "message": "Environment health check",
  "event": "environment_health_check",
  "environment": "Production",
  "status": "active|inactive",
  "error": "Connection timeout"  // Only present if check failed
}
```

**Event**: `health_check_completed`

Logged when all environment health checks complete.

```json
{
  "timestamp": "2024-01-15T10:30:45.123Z",
  "level": "info",
  "message": "Environment health check completed",
  "event": "health_check_completed",
  "activeCount": 2,
  "inactiveCount": 1,
  "totalCount": 3
}
```

### Configuration Events

**Event**: `configuration_reload`

Logged when configuration is loaded or reloaded.

```json
{
  "timestamp": "2024-01-15T10:30:45.123Z",
  "level": "info|error",
  "message": "Configuration reload",
  "event": "configuration_reload",
  "reason": "startup|file_change",
  "success": true,
  "error": "Invalid JSON"  // Only present if failed
}
```

**Event**: `spec_cache_clear`

Logged when Swagger specification cache is cleared.

```json
{
  "timestamp": "2024-01-15T10:30:45.123Z",
  "level": "info",
  "message": "Swagger specification cache cleared",
  "event": "spec_cache_clear",
  "cacheSize": 3
}
```

### Server Events

**Event**: `server_start`

Logged when the server starts.

```json
{
  "timestamp": "2024-01-15T10:30:45.123Z",
  "level": "info",
  "message": "Server started",
  "event": "server_start",
  "port": 3000,
  "environment": "development"
}
```

**Event**: `monitoring_start`

Logged when environment monitoring starts.

```json
{
  "timestamp": "2024-01-15T10:30:45.123Z",
  "level": "info",
  "message": "Environment monitoring started",
  "event": "monitoring_start",
  "environmentCount": 3
}
```

## Request Tracing

Each HTTP request is assigned a unique request ID that is:

1. Generated by the `requestIdMiddleware`
2. Attached to the request object as `req.requestId`
3. Included in the response headers as `X-Request-ID`
4. Included in all log entries related to that request

This allows you to trace a request through the entire system by filtering logs by request ID.

### Example: Tracing a Request

```bash
# Filter logs by request ID
cat logs.json | grep "abc123..."

# Using jq for better formatting
cat logs.json | jq 'select(.requestId == "abc123...")'
```

## Log Levels

- **info**: Normal operational events (submissions, validations, status changes)
- **warn**: Warning conditions (validation failures, missing configuration)
- **error**: Error conditions (email delivery failures, system errors)
- **debug**: Detailed diagnostic information (individual health checks)

## Usage in Code

### Import the Logger

```javascript
const {
  generateRequestId,
  LogLevel,
  log,
  logErrorSubmission,
  logValidationResult,
  logEmailDelivery,
  logEnvironmentStatusChange,
  logEnvironmentHealthCheck,
  logConfigurationReload,
  logError
} = require('./utils/logger');
```

### Log Error Submission

```javascript
logErrorSubmission(requestId, errorRequest, 'received');
```

### Log Validation Result

```javascript
logValidationResult(requestId, validationResult, endpoint, method);
```

### Log Email Delivery

```javascript
logEmailDelivery(requestId, 'sending', 1, endpoint, recipients);
```

### Log Environment Status Change

```javascript
logEnvironmentStatusChange('Production', 'active', 'inactive');
```

### Log Custom Events

```javascript
log(LogLevel.INFO, 'Custom event', {
  event: 'custom_event',
  customField: 'value'
});
```

## Log Analysis

### Using jq

```bash
# Count events by type
cat logs.json | jq -s 'group_by(.event) | map({event: .[0].event, count: length})'

# Find all failed validations
cat logs.json | jq 'select(.event == "validation_result" and .isValid == false)'

# Find all email delivery failures
cat logs.json | jq 'select(.event == "email_delivery" and .status == "failed")'

# Count logs by level
cat logs.json | jq -s 'group_by(.level) | map({level: .[0].level, count: length})'
```

### Using grep

```bash
# Find all error-level logs
grep '"level":"error"' logs.json

# Find all logs for a specific endpoint
grep '"/api/users"' logs.json

# Find all environment status changes
grep '"event":"environment_status_change"' logs.json
```

## Best Practices

1. **Always include request ID**: Use the request ID from `req.requestId` in all logs related to a request
2. **Use appropriate log levels**: Don't log everything as INFO
3. **Include relevant metadata**: Add context that will help with debugging
4. **Don't log sensitive data**: Avoid logging passwords, tokens, or PII
5. **Use event types consistently**: Stick to the defined event types for consistency
6. **Log at decision points**: Log when important decisions are made (validation pass/fail, retry attempts, etc.)

## Integration with Log Management Systems

The JSON format makes it easy to integrate with log management systems like:

- **ELK Stack** (Elasticsearch, Logstash, Kibana)
- **Splunk**
- **Datadog**
- **CloudWatch Logs**
- **Papertrail**

Simply configure your log shipper to parse JSON logs and forward them to your log management system.
